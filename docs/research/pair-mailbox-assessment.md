## Mechanism matrix

| Mechanism | Value in pair-mailbox | Transferable idea | TALOS implementation | Decline / limit |
|---|---|---|---|---|
| Writer / Critic roles | Keeps implementation ownership and review authority visible; the critic is read-only. | Separate write permission from review and make the reviewer's finding consequential. | Persist a single-writer lease and an independent review state; give critic a read-only checkout or OS-enforced read boundary. | Do not copy MCP role claims, shared-room role names, or peer-elected authority as TALOS's authorization model. |
| Competitive phase protocol | Makes plan, implementation, review, verification, and closeout explicit; reviewers can disagree with evidence. | Durable, checked state transitions and meaningful rejection loops. | Rust state machine validates every SQLite transition; critic findings reopen implementation with a new revision. | Do not reproduce dozens of pair-specific tools or require the model to self-report gate evidence. |
| Single-writer lock | Prevents two enrolled roles from silently editing the same checkout. | Atomic ownership, stale-owner detection, and refusal reasons. | SQLite transaction plus expiring lease/fencing token and recorded OS process identity. | No text-only `pair_claim` race. Worktree alone is not a write-authority lock. |
| Sealed patches + SHA-256 | Detects patch substitution between proposal and application; the writer rechecks immediately before apply. | Bind a reviewed artifact to exact bytes and verify at the trust boundary. | Store patch digest and target revision; verify exact bytes and repository base before applying. | Do not store an unbounded shared patch directory or use a mailbox server as the authority. |
| Ground truth / anti-mock | Compares claims with Git tree facts, dirty hash, stubs, and actual test records; green superficial tests do not certify connectivity. | Derive completion evidence from observable tree/process/check results. | TALOS records command, cwd, start/end, exit status, revision, and output digest; independently verifies Git diff and test artifacts. | Do not port regex-based anti-mock verdicts as a universal correctness oracle. Tests of a fake adapter are not proof that a vendor CLI works. |
| Task planning and queue | Durable task list, asymmetric close rights, leases, idempotency keys, and recovery of expired work are documented and tested. | Stable task IDs, append-only events, atomic claim/renew/reclaim, and visible open work. | SQLite WAL task queue with compare-and-set lease, attempt history, acceptance criteria, and idempotent recovery. | Do not copy the legacy JSON-to-SQLite migration markers or compatibility layers; TALOS starts with a clean schema. |
| Recovery and `pairpilot` | Supervises silence, dead agents, permissions, pending delivery, and report generation; records refusals. | A supervisor must reconcile process liveness and state, distinguish silence from death, and explain every refusal. | Tokio supervisor observes child handles, deadlines, cancellation, exit code, and database lease; tmux is only the persistent terminal surface. | Do not use MCP as the wake channel, inject text into TUI composers, parse ANSI screens, or guess relaunch commands. MCP is client-driven and cannot itself start a client turn. |
| CLI sessions | Profiles expose per-CLI flags; the recent recovery audit found that session resume is not interchangeable with restarting a process. | Probe public capabilities per installed version and persist returned session IDs. | Adapter-specific argument builder and capability record; test headless/resume/interactive handoff before enabling recovery. | Never inspect private session databases or claim headless-to-TUI context survival without a measured run. |
| Git worktrees | Provides workspace separation and task isolation; durable worktree events aid cleanup after failure. | Use isolated worktrees for truly parallel slices; journal their lifecycle and inspect before cleanup. | Add per-task worktrees only with explicit plan, lease, branch identity, and a recorded cleanup outcome. | Do not treat worktrees as a security sandbox or create one for every sequential edit. |
| Permission allowlist / OS sandbox | Shows that native CLI permissions, launch policy, and OS boundary must agree. Tests cover bypass-like strings and macOS/Linux process boundaries. | Fail closed; distinguish allowed routine work from system, secret, production, and destructive operations. | TALOS policy classifies operations and leaves each CLI's own controls enabled; optional OS sandboxing is an additional boundary. | Do not port the text-matching command allowlist: its own protocol acknowledges it cannot parse shell semantics. Do not add danger-skip flags to make Auto easier. |
| Native subagents and guilds | Delegation is bounded to a lead; helpers do not acquire shared write authority. | Parent owns the acceptance criteria, checks returned evidence, and merges work. | Model delegated work as child tasks with allowed paths, parent ID, dependency edges, and separate worktrees if concurrent. | Do not claim native subagent support where the CLI does not expose it; no generic cross-CLI subagent abstraction. |
| tmux and SSH | Keeps human sessions attached while roles run; recovery code has platform-specific process discovery. | Separate durable work from a terminal attachment; treat SSH loss as a client disconnect. | Database + supervised process are authoritative; optional tmux persists panes; reconnect displays current DB state. | Do not make tmux pane IDs or screen contents the only durable record. |

## History lessons used

- #106 added concrete role launch boundaries and autonomy policies; security flags vary by CLI. TALOS will preserve native permission controls and report the exact discovered mode.
- #107 added task persistence, leases, worker coordination, launch context, and startup resumption. It also documents why tasks cannot be represented by one mutable string and why expired work requires an idempotent reconciliation path.
- #108 fixed macOS process discovery and MCP restart behavior. The recovery acceptance record explicitly says a real Codex session resume and refreshed MCP catalog were still unproven at that point. TALOS treats platform process inspection and CLI session continuity as measured capabilities, not assumptions.
- The protocol has grown around live MCP, tmux, room identity, and legacy state compatibility. These solve pair-mailbox's own operating environment; TALOS is a fresh local Rust executable and will not port that architecture under different names.

## Decision

Transfer the invariants—exclusive writer, independent critic, digest-bound proposals, durable task claims, observed evidence, and recovery based on real process state. Rebuild them around typed Rust interfaces, transactional SQLite WAL, public CLI interfaces, and a local supervisor. Reuse no pair-mailbox code or state. The source repository remains untouched.
